# A captured ordinary card during portal fade

This is the original Grand Portal Main ↔ Island outbound sequence, with one physical mouse capture of a registered non-traveler material singleton. Its definition must be an ordinary material, with no crafting tail, no overlapping touch owner, no equipment/combat ownership, and no side effect from native save normalization. The board admits the original portal recipe and binds the capture to its actual card, receiver, departing session and fade generation.

The original TravelRecipe consumes first; GameDirector writes the departure save and copies traveler data before fade-out. GameData.StackData uses the current stack target. CardController continues sampling the mouse during Update while held; InputSystemUIInputModule sends physical Left Up to the stored pointerPress even if the fullscreen image now owns raycasts. CardController drops at the rendered pose, not the Up coordinates. Accordingly, Godot samples only physical motion for the old capture, uses the existing drop path once at the rendered pose, blocks fresh presses and discards the capture at scene replacement. The already serialized checkpoint and isolated destination candidate do not acquire any outgoing motion or drop changes. Arrival does not write a new checkpoint for this admitted case.

The native Godot test covers ordinary Wood landing on unoccupied space in both original boards, new Left Down, duplicated/emulated Up, and holding across black replacement. This is not acceptance of equipment, combat, held travel ingredients, mixed touch/mouse captures, terminal trades, chests, multi-card crafting tails, pointer ordering at exact Unity frames, physical hardware or Unity pixel parity. No original assets or screen captures are in the commit.
